**Title**

feat: allow the OAuth2 client assertion to be signed by an external signing service instead of a local private key

---

**Current zscaler-sdk-go version**

v3.8.48

---

**Description**

OneAPI private-key authentication currently requires the raw PEM. `Authenticate` -> `authenticateWithCert`
(`zscaler/oneapiclient.go`) calls `jwt.ParseRSAPrivateKeyFromPEM` and `token.SignedString(privateKey)`, so the
process must hold the private key itself.

The client assertion is a short-lived JWT the client mints (RFC 7523). The header and claims are assembled
locally and only the signature needs the key, so the signing operation can be delegated to whatever holds the
key, leaving the claim set and everything Zscaler sees unchanged.

Two shapes would cover the ground:

1. A `Signer` interface plus a `WithSigner` config setter, for callers who want to sign through a KMS SDK, an
   HSM, or anything else, without this module taking a dependency on those SDKs.
2. A configurable signing endpoint (HashiCorp/HCP Vault Transit, or a generic HTTP signing service), for
   consumers that cannot inject Go code - most importantly the ZIA and ZPA Terraform providers.

`Configuration` already carries an unused `PrivateKeySigner jose.Signer` field and a `WithPrivateKeySigner`
setter, which suggests something along these lines was already considered.

---

**Use cases**

Keys generated inside a KMS or HSM - HCP Vault Transit, Azure Key Vault, AWS or GCP KMS - have to be created
as *exportable* purely to satisfy this SDK. Many organisations' key management policies forbid exportable
keys outright, which today forces a choice between using OneAPI private-key authentication and complying with
key policy.

Delegating the signature removes the conflict: the key is generated non-exportable, the signing service
performs the RS256 operation, and the SDK only ever handles signatures.

This reaches most people through the Terraform providers, which pass `private_key` straight through to this
SDK, so the provider configuration is where the exportable-key requirement actually bites.

---

**Potential zscaler-sdk-go usage**

```go
// 1. Any signer: a KMS SDK client, an HSM, a signing gateway.
cfg, err := zscaler.NewConfiguration(
    zscaler.WithClientID(clientID),
    zscaler.WithVanityDomain(vanityDomain),
    zscaler.WithSigner(mySigner), // Sign(ctx context.Context, signingInput []byte) ([]byte, error)
)

// 2. Configured declaratively, so non-Go consumers (the Terraform providers) can use it too.
cfg, err := zscaler.NewConfiguration(
    zscaler.WithClientID(clientID),
    zscaler.WithVanityDomain(vanityDomain),
    zscaler.WithSigningConfig(remotesign.Config{
        URL:          "https://vault.example.com/v1/transit/sign/zscaler-oneapi",
        Namespace:    "admin",
        AuthMethod:   remotesign.AuthMethodVaultJWT,
        Role:         "zscaler-terraform",
        JWTTokenFile: "/var/run/secrets/tokens/vault-token",
    }),
)
```

The signing service receives only the assertion's signing input (`<header>.<claims>`) and returns a signature;
the claims are identical to the ones `authenticateWithCert` produces today.
